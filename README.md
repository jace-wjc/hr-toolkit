# HR Toolkit

人事 Excel 自动化工具箱。当前已落地：
- **需求1：社保明细与汇总**
- **需求2：考勤与周月报统计**
- **需求3：保险台账与增减预警**
- **需求4：工资表按入职公司拆分**
- **需求5：多月工资合并个人薪资汇总**
- **需求6：异动表汇总与花名册更新**
- **需求7：档案移交表入库与导出**
- **需求8：人员资料文件夹改名**
- **需求9：员工资料收集与本地离线 OCR 打包**

---

## 已实现工具

### 需求1-社保明细与汇总

输入社保账户缴费清单、常见压缩包，或一个包含多个社保清单/压缩包的文件夹，再选择参保人员花名册，按身份证关联人员信息，输出社保明细表和社保汇总表。输入支持 `.xlsx`、`.xls` 以及 ZIP、RAR、7Z、TAR 压缩包。

输出内容：

- 自动识别老 `.xls` 长表、单险种明细表、宽表缴费清单
- 按身份证匹配参保人员花名册
- 账单期按账户归集。费用所属期优先取明细行，再取表头注明的期间、文件名和外层目录名，跨月明细可以有各自的所属期
- 源表标明缴费性质时以源表为准。其余记录默认把大于 0 且低于 500 的基数按补差处理，特殊地区可在界面取消勾选。各险种只显示自己的实际补差期间，没有有效期间的表头不带日期
- 社保缴纳地、缴纳单位优先按账单文件夹或文件名识别；与花名册不一致时会提醒
- 生成总的 `社保明细表.xlsx`
- 按参保单位/参保地额外拆分明细表，例如 `唐人四川-社保明细表.xlsx`、`唐人长春-社保明细表.xlsx`
- 生成 `社保汇总表.xlsx`，包含总汇总、按公司汇总、按缴纳单位/参保地/险种/项目的数据分析和异常提醒
- 未匹配花名册的人员、姓名不一致、未识别账单期会在日志和异常提醒中列出

公积金、残保金、管理费暂无数据时留空；后续人事提供单独数据后可继续补充。

### 需求2-考勤与周月报统计

输入 HR 系统导出的考勤结果、周报记录、月报记录，支持单个文件、多个文件、常见压缩包，或包含这些文件/压缩包的文件夹，自动生成考勤和周月报统计表。输入支持 `.xlsx`、`.xls` 以及 ZIP、RAR、7Z、TAR 压缩包。

输出内容：

- 自动识别 `考勤结果`、`周报记录`、`月报记录`
- 生成 `考勤统计`，汇总事假、病假、带薪休假、调休、各月加班、旷工、迟到/早退、漏打卡和备注
- 生成 `考勤异常明细`，列出漏打卡、加班、调休、迟到/早退、旷工等明细
- 上传 `应汇报人员名单` 后，考勤、周报、月报都只统计名单内人员，考勤按名单顺序展示。留空则处理所选原始资料中出现的全部人员
- 生成 `周月报统计`，统计未写周报、周报超时、未写月报、月报超时，不计算扣款金额
- 生成 `周月报异常明细`，列出异常人员、周期、截止时间、实际汇报时间和来源文件
- 周报截止为次周一 `17:00:59` 前正常、`17:01` 起超时；月报按次月 2 日同样规则判断
- 在“周月报设置”里分别选周报和月报的起止日期，可用日历、手动输入或快捷按钮。周报选范围时，只统计截止周一落在范围内的各期，并排除起始日以前的提交。留空时先取文件名的日期范围，否则从最早提交所在月的 1 日取到最后提交日。要核对整月，请明确选齐整月日期
- 月报按实际提交日期筛选，包含首尾两天。留空时使用全部月报记录
- 输出 `考勤周月报汇总表.xlsx`

想找出从未交过周报或月报的人，请提供完整的应报名单。仅凭提交记录无法确定还有谁应交。

**考勤公司和历史加班**

- 多家公司可以一起导入。出现“补充考勤人员信息”时，选同公司、同驻地的人员，填写公司和实际工作地点，核对规则后继续。同一文件内有不同驻地时切换到“按人员”。在“管理识别规则”可维护公司、驻地和已保存的人员选择
- 默认按公司和驻地匹配规则。整批人员共用规则时，可选“统一设置，可添加人员例外”，再填写有效期和每天工时
- 做 9 月考勤时，“历史考勤汇总”可选人事已核对的 8 月汇总表。旧表只有累计列扣过调休时选“尚未抵扣”，各月已手工改成余额时选“全部已人工抵扣”。仅部分人改过时选“部分人员已人工抵扣”并列出这些人
- 工具先用最早仍有效的旧月加班抵扣调休，再结转未到期的各月余额。有效期可选 3、6 或 12 个月，未到期可跨年。天数按适用规则以每天 7 或 8 小时换算。余额不足也会生成结果，并高亮标注待核对，不借用以后月份的加班
- 本次事假、病假、调休和日常备注取本次资料。在“考勤设置”可选择加班和调休备注按天或按小时显示，也可增加公出、出差列

**周报算哪一期，按提交时间判断**（以截止时间周一 6.15 17:00 为例）：

| 提交时间 | 算哪一期 | 统计表显示 |
| --- | --- | --- |
| 上周五 0:00 ～ 周一 17:00:59 | 6.15 这期 | 正常 |
| 周一 17:01 ～ 周一 23:59 | 6.15 这期 | 超时（如“17:30提交”） |
| 周二 ～ 周四 | 6.15 这期的补交 | 超时（如“6月17日9:05提交”） |
| 周五 0:00 起 | 下一期（6.22 截止） | 下一期正常 |

**周报归属和月报日期举例**

- **上一期已经交过，周二到周四又交了一份**：这份视为提前交的下一期周报，不记超时，下一期也不会记未写。例如小王 6.15 周一按时交了，6.18 周四因为要请假提前把本周的交了，那 6.22 那期就算他已交。
- **归属期超出所选日期范围。** 6 月 26 日（周五）提交的周报属于 6 月 29 日截止那期，范围选到 6 月 24 日时不计入。下次要统计这份早交记录，起始日应在 6 月 26 日或以前，范围也要包含 6 月 29 日。
- **月报范围跨月。** 月报按起始月份确定截止日。例如选择 9 月 6 日至 10 月 24 日，9 月 1 日提交的记录会排除，本次核对的 9 月月报截止到 10 月 2 日 17:00。

### 需求3-保险台账与增减预警

选择各保单人员清单及含有花名册的人力资源分析表，生成保险台账。保单可选单个或多个 Excel、常见压缩包，或包含这些资料的文件夹。

输出内容：

- 自动识别保单号和保单人员
- PZDX 类保单的保额取 `每人伤残死亡限额`，按万元显示
- PEAC 类保单没有明显保额字段，固定按 `60` 万元显示
- `项目/部门` 从人力资源分析表的 `花名册` 工作表补充，优先取 `部门/项目` 列
- 生成人员增减预警：花名册在职但保单没有提示 `需加保`，保单有但花名册没有或已标记离职提示 `需减保`
- 输出 `保险台账.xlsx`，包含 `保险台账` 和 `人员增减预警` 两个工作表
- 如存在 `需加保` 人员，会额外输出 `人力资源分析表_保险预警.xlsx`，在 `花名册` 中标记 `保险预警`

人事已确认岗位保险规则暂取消，当前只做台账明细和人员增减预警。

### 需求4-工资表按入职公司拆分

输入一个包含 `汇总表`、`明细表` 的工资表，按明细表中的 `入职公司` 字段拆分为多个 Excel 工作簿。输入支持 `.xlsx` 和 `.xls`。

工作表或列被改名时，在确认窗口选择实际的汇总页、明细页，并按样例确认相应列。完成后点“打开结果目录”查看各公司的工资表。

输出内容：

- 每个入职公司一个独立 `.xlsx`
- 保留原工资表的主要样式、表头、公式结构
- 明细表只保留对应公司的员工行
- 明细表保留原模板分段小计和底部总计文案
- 汇总表引用拆分后明细表中的分段小计

### 需求5-多月工资合并个人薪资汇总

输入单个月度工资表、多个工资表、常见压缩包，或一个包含多个月度工资表/压缩包的文件夹，按 `身份证号码` 合并，输出每个人一行的个人应发工资汇总表。也可以同时选择已有汇总表，工具会把新月份追加进去。输入支持 `.xlsx`、`.xls` 以及 ZIP、RAR、7Z、TAR 压缩包。

明细表的应发金额支持 `应发小计` 和 `本月应发工资`（同时存在时优先使用前者）。优先读取 Excel 已保存的计算结果；新格式拆分后无缓存时，支持按原公式 `ROUND(SUM(本行收入区域)-SUM(本行扣款区域),2)` 计算，包括输入项中的本行引用和基本四则运算。无法安全计算的公式会提示用 Excel/WPS 重新计算并保存，不会套用旧模板列号。月份仍优先从文件名识别，文件名无月份时读取表内日期，请保持两者一致。

Qt 桌面端支持客户自行设置列头对应关系：

1. 选择工资表后点“开始合并”。已识别的模板自动处理。必要列改名、重名或旧设置无法唯一定位时，在“确认列名”中选择实际对应列。
2. 在下拉列表中选择原表的姓名、身份证号码、应发工资列，并核对列字母、列头和样例。例如可将 `应发小记`、`本月应发合计` 对应到“应发工资”。已有汇总表可单独设置姓名和身份证号码列，月份列仍按原有规则识别。
3. 同一次可混合导入多种模板。使用弹窗上方的模板列表逐个确认，同类模板只需选一次。勾选“记住本项目的选择”可在当前项目复用多套对应关系。表头变化或对应列有歧义时仍需确认。
4. 如果列表里没有正确的列，请选实际工作表、调整表头行，再点“读取这些列名”。
5. 要重新设置已识别的模板，先选择相应工资表，打开“模板设置”，切到“本次文件确认”，点“开始检查并处理”。修改对应列或点“恢复自动识别”，核对全部模板后确认继续。

桌面端不会静默跳过未确认的模板。确实不需要合并的文件，应明确勾选“本次不合并”，结果会增加“未合并文件”工作表供核对。列头确认后原文件发生变化时，需要重新确认。自定义对应关系只决定读取哪一列，不修改原表，也不改变金额含义；没有有效计算结果且无法安全计算的公式，仍需先在 Excel/WPS 中重新计算并保存。命令行保留原有调用方式，不读取桌面端的项目设置。

输出内容：

- 自动识别每张工资表的月份
- 按身份证号码合并同一员工
- 已有汇总表中同一人同月的非零金额会保留，空白或 0 可补入。本次导入的同人同月多条明细会累加并提醒
- 新月份中出现的新员工会自动新增一行
- 人员在某个月没有工资时自动填 `0`
- 输出 `个人薪资汇总表.xlsx`

### 需求6-异动表汇总

输入单个项目异动表、多个项目异动表、常见压缩包，或一个包含多个项目异动表/压缩包的文件夹，将各项目填写的 `增补表`、`离职`、`转正`、`调整` 按记录日期分到对应月份汇总表。文件夹里如果同时放入人力资源分析表，工具会同步更新其中的 `花名册`。输入支持 `.xlsx`、`.xls` 以及 ZIP、RAR、7Z、TAR 压缩包。

输出内容：

- 支持项目表中的 `增补表`、`离职`、`转正`、`调整`
- ZIP、RAR、7Z、TAR 会自动识别并解压，文件夹内的压缩包也会自动处理
- 不选择已有汇总表时，会按月份新建干净汇总表
- 选择已有汇总表文件或汇总表文件夹时，会按月份追加新记录，不会清空原记录
- 对应月份没有已有汇总表时，会自动创建该月份汇总表
- 已存在的异动记录不会重复追加，只会补充已有行中的空白字段
- 月份规则：增员看 `入职日期/入职时间`，减员看 `离职日期`，转正看 `转正日期`，调动看 `调整日期`
- 忽略模板中只有预填序号、没有填写内容的空行
- 汇总后重新编排各 sheet 序号
- 保留模板工作簿样式
- 按记录月份输出，例如 `2026年4月异动汇总表.xlsx`
- `增员` 会插入花名册对应项目后方，`减员` 会在花名册中标黄
- GUI 中可切换到 `花名册更新` 页，单独选择异动汇总表和人力资源花名册进行更新

薪酬、产值和同行对比分析页不参与本次汇总，可在日志核对哪些工作表已跳过。

**异动流程核对**

在“异动流程核对”选择同一事业部的入职、离职流程文件，再选择工具生成的异动汇总表。核对月份可留空，工具按汇总表内的入职、离职日期判断。离职默认取实际离职日期，只有业务口径明确时才切换为预计日期。

公司简称有歧义时点“管理对应规则”。地市、所属专业或项目写法不同时，只勾选确实同义的名称，保存后可在“管理名称规则”中调整。核对完成后看报告的“核对说明”和“预警明细”。启用高亮时，汇总表副本里浅绿是本次补齐的空白，浅黄是双方已有值的差异。入职报备日期与实际到岗日期不同会提示，明确匹配的记录仍可补齐空白资料。

### 需求7-档案移交表入库

输入项目部提交的人事档案移交表，按 `公司` 写入档案汇总表；也可以从一份或多份档案汇总表生成各公司独立档案表。

输出内容：

- 支持单个 `.xlsx/.xls` 移交表、多个移交表、ZIP/RAR/7Z/TAR 压缩包，或包含移交表/压缩包的文件夹
- 按 `公司` 自动写入档案汇总表对应工作表
- 已有档案汇总表可选；不选择时使用内置空模板新建汇总表
- 身份证已存在时不重复新增，只补充原汇总表中为空的材料字段
- 档案汇总表缺少公司工作表时，会按第一个工作表样式自动创建
- `编号` 从文件名、表头标题或公司名识别项目地区，例如 `茂名项目部` 自动填 `11`
- 要改用本项目的地区编号，点页面上方“地区编号维护”。同地区或同编号优先使用自定义项，删除该项后恢复相应内置设置
- `档案号` 使用模板公式按 `编号-入职公式-出生年月公式-序号` 生成
- 档案表中有、汇总表没有的字段会汇总到 `其他`
- 档案入库输出 `档案表汇总表.xlsx`
- 档案表生成支持选择已有公司档案表；匹配到公司就追加，没匹配到就用内置干净模板新建
- 生成公司档案表时会自动改标题公司名，并为新增人员补边框、居中和公式
- 档案表生成会按公司输出 `公司名-档案表.xlsx`

### 需求8-人员资料文件夹改名

选择一个人员资料目录，对目录下的人员文件夹或指定类型的文件（PDF、图片、文档）做批量改名。执行前会先预览，并二次确认。

支持内容：

- 选择项目类型：文件夹、PDF、图片、文档，或全部
- 批量追加后缀，例如 `张三` -> `张三-劳动合同`（追加文字会按原样写入，建议以 `-` 或 `_` 开头）
- 批量删除结尾文字，例如 `张三_劳动合同`、`李四劳动合同` -> `张三`、`李四`
- 指定单个人员/单文件处理，例如只处理 `张三` 或 `张三.pdf`
- 替换单个名称，例如 `张三` -> `章五`；替换文件时会自动补全原扩展名
- “替换指定文字”和“规范名称格式”可按文件类型批量处理。Excel 改名可按名单顺序分配姓名，也可按“原文件名”和“新名称”两列逐项匹配
- 点“预览”可搜索、筛选、改写拟用名称或排除项目。顺序改名可上移、下移调整姓名。点“确认并执行此方案”后，在本批“处理结果”中查看改名副本、改名记录和 CSV 清单

### 需求9-员工资料收集与本地离线 OCR 打包

选择待整理的原始混乱员工资料总目录，自动按目标员工名单（支持上传花名册 Excel 或手动输入人员信息）进行材料识别、分类和归档打包。

核心功能与特性：

- 按人分文件夹时，勾选“全部”会提取匹配人员的整个文件夹。只要指定材料时，取消“全部”并勾选所需类型。常用材料可保存为组合
- 文件混放时选“无序平铺资料库（OCR 索引）”。识别在本机执行，索引默认存放在当前用户缓存目录，后续复用未变化文件的结果
- 无序资料按可用的身份证号码、手机号或姓名等线索匹配。名单中有重名时，请补充能区分人员的信息，并在结果中核对归属
- **多类别材料自动分类**：自动归类身份证（正反面）、体检报告、劳动合同、银行卡、学历证书、离职证明等材料；

## 桌面版使用

无参数启动时会打开图形界面：

```bash
python3 -m hr_toolkit
```

界面操作流程：

1. 首次使用时通过“新建工作项目”填写名称并确认保存位置，或打开电脑上已有的项目文件夹
2. 在左侧选择工具，再从电脑添加文件、压缩包或文件夹
3. 在中间区域核对已选择的资料，可以右键打开原文件或所在文件夹。有“最近使用”的输入项可以直接重新选择以前用过的文件或目录
4. 点击当前工具的处理按钮。若提示确认工作表、列名或人员规则，核对后继续。资料文件夹改名先点“预览”，再确认执行
5. 完成后点“打开结果目录”，或在右侧“项目文件”按工具和批次查找“处理结果”。原文件在原位置读取和保管，重新处理时需再次找到原件

**工作表和列名变化时**，按预览选择数据所在的标签页或列。只多出无关页时，日志列出未处理工作表。普通列名确认默认只对本次有效，像 `222` 这样可能变换含义的表头可以保持默认。固定模板可勾选记住。在“模板设置”中可管理常用列名、工作表名及已记住的选择，多月工资模板按上文的工资合并步骤调整。

**使用 Sage 时**，点 Sage 图标或按 `Ctrl+K`，按“去配置 API Key”的提示选择服务并填写密钥。可以提问、附加表格或截图，也可从“历史对话”继续。发送消息会将问题、上下文和选中的附件内容传给所选 AI 服务，项目文件只有主动附加才会随消息发送。

**给同事发安装包时**，点“更新记录”右侧的“复制下载地址”，按对方电脑选择 Windows 7 或 Windows 10/11，复制的始终是最新版地址。Mac 及其他系统请向管理员索取安装包。“设置”可切换中英文和深浅色外观。

### 项目文件工作区与追溯

一个项目可以使用全部人事工具。新批次按业务、工具和批次保存处理结果。以前版本已保存的上传资料仍可从原批次查看。

新建和打开项目共用目录校验。系统用户目录信息异常时，程序会尝试从操作系统读取当前账户的实际目录；损坏的最近项目记录会提示重新选择原项目文件夹，不会当作当前目录打开。保存位置失效时可重新选择，已有项目资料无需重建。项目创建和打开失败会记录完整错误堆栈，便于排查。

```text
项目名称/
├─ 业务分类/
│  └─ 工具名称/
│     └─ 处理批次/
│        ├─ 处理结果/
│        └─ 补充资料/   # 有补充文件时才创建
├─ 共用资料/
└─ .hrtoolkit/    # 隐藏的项目标记、批次清单、锁和回收站
```

- 新建项目弹窗会同时显示最终位置、留存内容和位置风险；活动项目只允许放在本机普通文件夹，网盘、共享盘、NAS、U 盘和移动磁盘请仅在退出工具后用于备份
- 项目位置由用户选择，项目资料与程序安装目录分开，正常更新或重新安装不会自动删除项目
- 新批次直接读取选定的原件。源文件移动或改名后，从新位置重新选择即可
- 项目内的“处理结果”是正式版本，工具不再向隐藏目录重复复制；如需发送，可从右侧打开后复制文件
- 右侧“添加”菜单中的“选择处理文件”和“选择处理文件夹”会把选中的资料带入本次处理。要复用已有项目资料，在右侧选中文件，点“带入当前工具”并选择用途
- 已有批次保留的上传资料、补充资料和结果仍可查看。升级前单独归档的资料可在“旧版记录”中查找
- 文件复制、校验和索引在后台分批进行；项目文件区每次启动默认收起，展开后文件树只读取当前层级，避免大项目拖住界面
- 每个批次和普通资料导入都有独立恢复记录；如果复制、登记、批次改名、移入回收站或从回收站恢复时程序意外退出，下次打开项目会按记录安全补完或明确停止，不会覆盖冲突文件；更高版本的项目只读打开，不会擅自改写
- 所有受支持压缩包在解压前都会检查文件数、单文件大小、总大小、重复路径、链接和异常压缩比例，超过安全限制会停止处理
- 输入压缩包后缀包括 `.zip`、`.rar`（RAR/RAR5）、`.7z`、`.tar`、`.tar.gz/.tgz`、`.tar.bz2/.tbz2`、`.tar.xz/.txz`；当前按普通单卷、无密码压缩包处理，加密包会明确提示而不会产生不完整结果
- “移到回收站”会将整个批次中实际保存的文件一起移入项目回收站。可在右侧“回收站”中搜索并恢复批次，同名时使用新名称
- 项目功能不会主动上传资料；如需把完整项目备份到 OneDrive、企业网盘、NAS 或 U 盘，请先退出 HR Toolkit，再按公司的数据安全规定复制项目文件夹

需要迁移或备份时，请先退出 HR Toolkit，再完整复制项目文件夹（包括隐藏的 `.hrtoolkit`）；不要单独编辑或复制正在使用的项目元数据和批次清单。

## 本机 CLI 验证与调用

日常 GitHub CI 按本次变更选择测试，不再每次运行整个测试套件：公共路径、项目存储、进程等模块会连同相关调用方一起验证；只修改文档时跳过运行时任务。Python 语法检查只覆盖变更文件，Win7 测试仍限定在既有兼容范围内。依赖审计在依赖文件变更或手动全量验证时执行，Qt/OCR 启动检查按相关模块选择。

需要全量验证时，在 GitHub Actions 的 **CI → Run workflow** 中勾选 `full_tests`。不勾选时，手动运行仅检查所选分支最后一次提交；普通推送覆盖推送中的全部提交，PR 覆盖相对目标分支共同祖先的变更。每次选择的范围会列在 CI 运行摘要中。发布标签仍保留原有全量验证，安装包范围不变。

测试映射维护在 `scripts/ci_scope.py`。新增业务模块或修改公共模块调用关系时同步更新映射；未映射的应用 Python 文件会明确报错，不会自动升级为全量测试。辅助脚本没有对应测试时仅检查语法。本机验证仍遵循 `AGENTS.md`，以上规则不授权本地自动运行测试或构建。

- CLI 文字替换遇到目标已存在、重复（含仅大小写不同）或名称无效时，整批不执行；执行期间出错则停止并列明已完成和未处理项目，不覆盖目标。
- 桌面端仍先预览、确认，再在项目结果副本上执行；CLI 不加 `--apply` 只预览，加上后直接修改指定目录中的名称。
- 现有 `replace` 仍按完整原名称精确匹配，追加、删除结尾文字、Excel 改名保持原有行为。

桌面端完整预览：

- 所有改名模式先生成完整方案，在独立预览窗口中查看全部项目、原名称、新名称、相对路径和问题；列表按需渲染，搜索和状态筛选不会自动排除隐藏行。
- 可以逐项勾选/排除，并直接编辑拟用名称；文件扩展名单独显示且不可编辑。每次调整会重新检查无效名称、重复名称、Windows 大小写冲突和目标占用。
- Excel 顺序模式的“上移/下移”只交换相邻项目分配到的姓名，文件行和扩展名不动；搜索或筛选期间禁止移动，避免误改不可见的行。
- “确认并执行此方案”以最终映射为准，不再读取 Excel 行序或重新生成名称。执行前再次检查源内容和目标占用；全部已选项目通过后才开始。
- 被选中的项目之间可以交换名称；先暂存，再以系统排他改名完成最终名称，不覆盖其他项目。异常或取消时尝试恢复原名；被外部程序占用或更改的路径不会被强行覆盖。
- 成功结果批次包含 `改名记录_*.jsonl`（确认方案、内容指纹和逐项执行事件）及 `改名清单_*.csv`（实际状态）。失败或停止批次沿用项目隔离规则，运行记录显示隔离位置；保留其中的中断现场和未恢复项目，历史批次的一键恢复暂未提供。源文件仍保持原样。
- 新增“按 Excel 原文件名匹配”：默认列名为“原文件名”和“新名称”，可自定义列名，表头须在前 20 行。完整原文件名必须唯一；新名称可带原扩展名，也可省略原扩展名。匹配不区分大小写，未匹配文件不会自动套用后续行。
- 新增“规范名称格式”：单独选择去首尾空格、合并空格、统一横线/下划线；先预览，不删除文档状态等业务文字。

上述交互预览和新模式属于桌面端；现有 CLI 调用及其输出格式保持不变。

`flat_ocr` 首次运行会在当前用户的缓存目录 `HRToolkit/material-index` 中按资料库分别保存索引，后续查询复用内容未变化的文件。索引仍含匹配所需的姓名、相对路径和脱敏识别摘要；保留原有 90 天未使用条目清理及体积限制。可从运行结果查看缓存位置，退出程序后删除相应索引可重建识别结果。旧资料库根目录的 `.hr_material_index_cache.json` 首次读取后改存用户目录，旧文件原件保留并提示资料库管理员处理权限或清理，避免影响其他使用者。显式指定共享缓存位置时仍需限制访问范围。源文件不会被修改。

### 精确 A/B 回归验收

修改 Excel 处理或文件处理实现前，先保存“修改前输出 + 客户源附件”的本地基线：

```bash
python3 scripts/compare_regression_outputs.py capture \
  --outputs "/path/to/before-output" \
  --sources "/path/to/source-copy" \
  --manifest "/tmp/hr-toolkit-baseline.json"
```

使用同一批输入生成修改后结果，再做验收：

```bash
python3 scripts/compare_regression_outputs.py verify \
  --baseline "/tmp/hr-toolkit-baseline.json" \
  --outputs "/path/to/after-output" \
  --sources "/path/to/source-copy" \
  --report "/tmp/hr-toolkit-regression-report.json"
```

工具会逐项比较工作表顺序、单元格值、公式及缓存计算值、格式、批注、链接、行列尺寸、合并区域、命名区域、打印区域与页眉页脚、验证规则、条件格式、表格、图表和嵌入资源；非 Excel 产物及全部源附件按字节大小和 SHA-256 验证。工具不会修改被检查的目录。基线会包含 Excel 业务值及附件哈希，应只保存在受控临时目录，不要提交到 Git 或对外发送。

## 自动构建与发布

本地发布脚本负责版本检查、测试、版本提交、annotated Tag 和原子推送。两种 Windows 安装包和 GitHub Release 由 GitHub Actions 生成。正式发布命令如下。

```bash
npm run release -- 0.9.1
```

命令会询问**本次更新内容**：每行填写一条，写完后输入空行结束，随后展示给你确认。填写的是用户实际会看到的新增功能、问题修复等，不会沿用上次内容，也不会自动把 Git 提交记录当成说明。确认发布后，脚本自动按版本保存；这些文字会用于更新前提示，以及安装后的“更新记录”。无需手动修改源码。

也可以直接传入本次内容：

```bash
npm run release -- 0.9.1 --notes "新增更新记录入口" "优化下载和安装进度提示"
```

上面的内容仅为写法示例，每次应填写该版本实际的改动。

首次使用先安装 Python 依赖和 Node.js。npm 入口会优先使用 `.venv/bin/python`，不存在时再使用 `python3`；两者之一必须能运行完整测试。发布前可执行不修改版本文件、commit、Tag 或远端的演练：

```bash
npm run release -- 0.3.5 --dry-run
```

无人值守环境需用 `--notes` 提供本次内容，审核后可追加 `--yes`；`--yes` 不会自动生成更新内容。发布脚本会严格检查 stable SemVer、clean `main`、`HEAD == origin/main`、本地/远端 Tag 冲突以及全部版本字段，并通过已登录的 GitHub CLI (`gh`) 确认当前精确提交的完整 CI 已成功；CI 尚未开始、运行中、失败或取消时都不会创建版本提交和 Tag。通过远端门禁后再运行 `unittest`、`compileall` 和 `git diff --check`。正式执行只会暂存 `hr_toolkit/__init__.py`、`package.json`、`package-lock.json` 和 `hr_toolkit/release_notes.py`，不会运行本地跨平台构建，也不会使用 `git add .`。版本号与本次更新记录一起提交，失败时按同样的保护规则回滚。

脚本创建单一版本提交和 `v<version>` annotated Tag，再通过一次 atomic push 同时推送 `main` 与 Tag。推送失败时只有在确认远端两个引用都未变化后才自动回滚；远端状态不明确时会保留现场，要求人工核对。

> 不要为了测试发布脚本在正式仓库创建 Tag。先使用 `--dry-run`；正式命令必须等发布负责人确认。

### GitHub Actions 产物

普通 push 和 pull request 由 `.github/workflows/ci.yml` 按变更范围运行测试、编译和发布检查。现代 Windows 使用 Python 3.12，Win7 兼容栈使用 Python 3.8。Win7 CI 车道在 Windows Server 2022 运行，Win7 SP1 实机验收另做。`.github/workflows/test-build.yml` 每周一北京时间 02:00 构建两种 Windows EXE，也可手动选择其中一种。依赖分别锁定在 `constraints/python312-production.txt` 和 `constraints/python38-win7.txt`。

`v*` Tag 触发 `.github/workflows/release.yml`。工作流检查 Tag 与 `hr_toolkit.__version__` 一致，分别构建并验证两种 Windows EXE，再发布 GitHub Release。GitHub 产物的单文件限制为严格小于 2 GiB。随后 `mirror-gitee` 同步源码、annotated Tag 和 `SHA256SUMS.txt`。供客户端自动更新的 `latest.json` 和两种 EXE 由发布维护者上传到对应版本的 Gitee Release。

当前 GitHub Release 的直接下载资产如下，`<version>` 表示版本号。

```text
HRToolkit_<version>_x64-setup.exe
HRToolkit_<version>_win7_x64-setup.exe
latest.json
SHA256SUMS.txt
```

MSI、macOS DMG 和便携 ZIP 暂停发布，恢复范围见 [项目协作规则](AGENTS.md#github-安装包临时范围)。

### Windows 安装与自动更新架构

现代安装包 `HRToolkit_<version>_x64-setup.exe` 面向 Windows 10/11 x64，使用 Python 3.12。兼容安装包 `HRToolkit_<version>_win7_x64-setup.exe` 使用 Python 3.8，对应 Win7 SP1 及 Windows 8/Server 2012 兼容通道。Win7 包携带 ONNX Runtime 1.11.1、app-local UCRT、VC 运行库和官方 7-Zip。两种包都内置 `HRToolkitUpdater.exe`。

两种 EXE 都安装到当前用户目录 `%LOCALAPPDATA%\Programs\HRToolkit`，普通用户双击安装无需管理员提权。同一台电脑只安装其中一种。Win7 用户首次切换时必须手动安装一次带 `win7_x64` 的安装包；之后程序会固定使用 `windows-x64-win7` 更新通道。不要再从网上单独下载或复制 `api-ms-win-core-path-l1-1-0.dll` 到程序目录，兼容包已经携带经过校验的运行时文件。

Win7 与 Python 3.8 均已停止官方维护，因此兼容分支只加载程序随包附带的可信 OCR 模型，不提供用户自定义 ONNX 模型入口；任何原生依赖升级都必须重新通过 PE 扫描和干净 Win7 虚拟机验收，现代分支不跟随该冻结版本降级。

Win7 发布验收在干净的 Windows 7 SP1 x64 虚拟机中运行 `scripts/smoke_win7_installer.ps1 -InstallerPath <安装包> -ExpectedVersion <版本号>`。脚本覆盖静默安装、运行库检查、主程序与更新器启动、OCR、压缩包、项目存储及卸载；另以合成密钥检查安装版 DPAPI 迁移和恢复，并检查离线更新清单的平台选择。更新改动还需从上一版 Win7 安装包实际检查、下载、安装并重启，记录主路径和 WinHTTP 回退的结果。离线检查不代表在线升级已通过。

**自动更新机制**：
- Windows 客户端在检测到新版本后，按当前系统选择安装包。Win7 清单必须有专用节点、包地址和哈希。缺少平台来源的旧缓存需要重新检查更新。
- 下载完成后唤起 `HRToolkitUpdater.exe` 并退出主程序；
- 更新器通过 `setup.exe /VERYSILENT /SUPPRESSMSGBOXES /NORESTART` 安装并重新打开应用；
- 保留对旧版 ZIP 解压更新的向后兼容。

### 国内更新源与手动安装

客户端的公开更新入口是 [Gitee 最新 Release 接口](https://gitee.com/api/v5/repos/optimistic-little-sunspot/hr-toolkit/releases/latest)，由它查找 `latest.json` 和对应的安装包。HTTPS 更新链路要求清单、包地址及重定向继续使用 HTTPS。Windows 仅在默认接口遇到特定 WAF 响应时用 WinHTTP 读取发布元数据。证书失败会报告错误，包下载仍由 Python 处理。

旧配置中的 `http://hr.seedlingintl.com/hr-toolkit/latest.json` 会在请求前迁移到上述 Gitee HTTPS 入口。其他 HTTP 更新源和由 HTTP 清单产生的旧下载缓存不再使用，请将 `update_url.txt` 或 `HR_TOOLKIT_UPDATE_URL` 改为有效的 HTTPS 地址。显式本地 `file:` 清单仍可用于离线验收，远程清单不能引用本机文件。

Gitee 资产未上传或连接失败时，可从正式 GitHub Release 手动下载对应的 EXE，并对照同版本 `SHA256SUMS.txt`。下载弹窗可以用右上角 `×` 或 `Esc` 取消，程序会清理未完成的临时文件。

## 运行日志与数据隐私

- **全离线计算**：所有数据统计、表格拆分合并、OCR 图像识别均在用户本机内存与本地磁盘中运行，不连接任何第三方 AI 云端或外部数据服务器。
- **脱敏日志**：
  - 运行日志统一输出至同级目录下的 `HRToolkit_app.log` 与 `HRToolkit_update.log`；
  - **仅记录工具启动、耗时、处理文件数量与错误堆栈，严禁记录任何真实表格内容（身份证号、手机号、薪资金额等敏感信息绝不上报与外显）**；
  - 日志设置自动滚动截断限制（最大 1MB），防止长期占用磁盘空间。

## AI 密钥存储

Win7 和 Win10/11 安装版的 API Key 使用当前 Windows 用户的 DPAPI 保护后写入配置。首次读取旧配置时原子迁移明文 Key，不生成明文备份；迁移失败保留原文件并提示重新保存。复制配置到另一台电脑或账户后可能需要重新填写 Key，无法解密时仍保留原密文和服务地址。该接口的系统要求见 [Microsoft DPAPI 文档](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata)。非 Windows 源码运行仍使用仅文件所有者可读写的配置文件，未新增系统钥匙串集成。

AI 对话保留最近 40 个，可在历史列表删除。读取旧对话和保存新对话时会脱敏可识别的证件号及表格证件列，附件原路径保持不变；图片本身不自动涂抹，仍需由用户确认内容。删除对话或裁剪历史后清理没有被其他对话及当前任务引用的应用图片缓存。若历史文件损坏、迁移失败或存在损坏备份，保留图片供恢复，不自动清理。历史文字仍可能含姓名等业务信息，记录保存在当前用户目录。

## 旧 Excel 文件转换

`.xls` 的纯数据读取仍优先使用 xlrd。自动保格式转换只接收能检查的 BIFF5/8 文件；发现 VBA、Excel 4.0 宏表、加密、异常结构或超过 128 MiB 时，停止本机转换并提示禁用宏后另存为 `.xlsx`。Excel/WPS 必须能设置并回读禁用宏和事件的选项；LibreOffice 使用独立的临时用户配置关闭宏执行。要求保留格式的工具不会静默降为仅数据转换。上述检查不等同于恶意文件沙箱，各 Office 版本的真实转换和 Win7 行为仍需验收。

## 性能复测

项目目录读取默认最多使用 2 个后台线程；慢盘设备可在启动前设置 `HR_TOOLKIT_SCAN_WORKERS=1`，支持范围为 1–4。该参数只控制项目文件树读取，业务写入仍由原有单任务协调器执行。文件列表元数据、输入校验和首次业务模块导入均在后台处理；进度在进入 Qt 事件队列前合并，每 100 ms 刷新一次，并在完成或失败时刷新最后进度。

压缩 Excel 根据 ZIP 目录记录的工作表 XML 体积选择进程隔离，达到 2 MiB 时使用独立业务进程，避免只看压缩后的文件大小漏掉重负载。工资拆分在完成快照和每份输出后释放不再使用的单元格，保留跨工作簿样式转换所需的样式表。

以下命令只生成和处理独立的合成数据。使用同一个 Python/Qt 环境、同一份输入目录，串行运行优化前后版本，避免把不同运行时或同时运行的基准当成性能提升。

```bash
# 模拟 1000 个路径各有 5 ms 磁盘延迟，记录 GUI 心跳与切换耗时
python scripts/benchmark_desktop_responsiveness.py --files 1000 --stat-delay-ms 5
# 实际 Qt Quick 窗口中的 3 万行虚拟滚动
python scripts/benchmark_qt_quick.py --files 30000 --workspace-files 30000 --mode scroll --scroll-target workspace --duration 4
# 准备一次，再分别指定旧源码与当前源码；保留输入 SHA-256 和完整 Excel 包成员哈希
python scripts/benchmark_business_pipeline.py --root outputs/business-benchmark --prepare
python scripts/benchmark_business_pipeline.py --root outputs/business-benchmark --source-root /path/to/baseline --label before
python scripts/benchmark_business_pipeline.py --root outputs/business-benchmark --label after
```

`benchmark_business_pipeline.py` 覆盖社保、商保、考勤、工资合并/拆分、异动、名册、档案导入/导出及目录重命名预览；`--profile` 可另外保存 cProfile 结果，不能与未启用 profiling 的耗时混比。输出哈希仅排除 Excel 创建/修改时间，仍包含所有业务 XML、公式、样式、合并区域和其他包成员。`benchmark_ocr_runtime.py --images /path/to/test-images --expected-text 测试姓名` 用真实图像验证 OCR 冷启动、连续识别耗时及 RSS；已有 `benchmark_material_search.py` 则衡量合成资料库的缓存命中路径，两者不能混用。

专项复测使用 `benchmark_followup_performance.py`：`footer` 覆盖已有 5000 行、表尾、空白行及重复记录的追加；`salary` 用 `--companies 2/10/50` 在准备阶段生成 2000 人的多公司输入；`cache` 衡量 3 万条合成缓存逐批新增时的清理与原子保存成本，不执行 OCR 推理。每种场景使用独立的 `--root`，每次运行使用不同的 `--label`；报告包含输入哈希和输出包成员哈希。

```bash
python scripts/benchmark_followup_performance.py --case footer --root outputs/footer-benchmark --prepare
python scripts/benchmark_followup_performance.py --case footer --root outputs/footer-benchmark --source-root /path/to/baseline --label before
python scripts/benchmark_followup_performance.py --case footer --root outputs/footer-benchmark --label after
```

异动汇总保持逐条去重和补齐规则，将表尾按实际新增行数一次性移回；资料索引复用 Windows API 绑定，但每个文件仍重新查询 ChangeTime，无可靠变更标记时仍计算内容哈希。缓存清理在单次检查点内复用最多 256 个时间戳解析结果，保持原有过期规则、保存频率和 JSON 格式。

Windows 与 macOS 构建脚本会打印各步骤耗时。默认仍完整清理构建；本地重复构建可给 `scripts/build_windows.py` 或 `scripts/build_macos.py` 追加 `--incremental` 复用 PyInstaller 缓存。增量模式保留相同的原生依赖、版本、架构和启动检查，不替代正式发布前的完整清理构建与目标系统验收。修改 Python、Qt、原生依赖或打包钩子后应重新进行完整清理构建。
