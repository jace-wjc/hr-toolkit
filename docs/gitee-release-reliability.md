# Gitee 发布末步失败记录与重试边界

## 已确认的两次失败

- v0.9.23：运行 `36370311737` 的首次尝试，任务 `108766640173` 在 Git 同步阶段报 `SSL connection timeout`。当时的重试匹配只覆盖 `timed out`，漏掉了 `connection timeout`。该运行后来重跑成功。
- v0.9.24：运行 `36536522747`，任务 `109303921860` 在查询 `/releases/tags/v0.9.24` 时收到 HTTP 403，正文是带 `baidu_waf_intercept_page` 的 HTML 防护页。源码和 Tag 已同步；发布接口查询没有重试，因此第一次失败就退出。
- 两次 GitHub 安装包构建和 Release 均已成功，不能把 Gitee 同步失败描述为安装包构建失败。

## 当前处理

- Git 传输补齐 SSL 连接超时识别，沿用最多 4 次、间隔 15/30/60 秒的重试；非快进、标签冲突、鉴权等失败仍然停止，禁止强推。
- Gitee API 查询、同内容更新、删除和公开附件读取，对网页防护 HTML 403、408/429、常见 5xx、超时、连接中断及不完整 JSON 做有上限的重试。JSON 权限拒绝、证书校验失败不重试，不关闭 TLS 校验。
- 创建 Release 不直接重复 POST。响应丢失或不完整时先按 Tag 查询：已经存在则复用；确认 404 才允许再创建；查询本身失败则停止。
- 附件上传保留“先查询是否已上传成功，再决定是否重试”，源码发行版仍只维护 `SHA256SUMS.txt`，不删除维护者手工上传的安装包。
- 公开可见性轮询不再叠加已耗尽的传输重试；持续失败仍非零退出，不添加 `continue-on-error` 或跳过发布校验。
- 错误日志区分网页防护和 API 权限问题，不再输出整段防护 HTML；令牌原文及 URL 编码形式均脱敏。

## 定向验证

使用本地模拟 HTTP 响应和临时本地 Git 仓库，不访问真实发布写接口：

```sh
.venv/bin/python -m unittest -v tests.test_gitee_git tests.test_gitee_mirror
```

2026-09-29：43 个用例通过，覆盖实际 HTML 403、SSL 超时、限流、永久权限错误、重试耗尽、响应丢失后的创建/删除、重复发布及保留手工安装包。将两个事故回归用例放到修改前源码运行，分别复现首次 403 退出和 SSL 超时未重试。

这不是对远端网络永不失败的保证。若 Gitee 持续拦截发布节点，退避重试仍会明确失败，需要检查节点访问或联系 Gitee 支持，不能靠隐藏错误解决。
