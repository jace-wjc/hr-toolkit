# 更新检查诊断日志

v0.9.25 仅增加本地诊断，未修改更新源、请求头、网络实现、TLS 校验、重试间隔及次数、自动下载规则或版本比较逻辑。后续网络兼容修复见本文末尾，不能将增强日志本身视为修复。

## 收集方法

在新版中正常点击一次“检查更新”。若失败，通过工具原有日志入口打开 `HRToolkit_app.log`，提供该次 `[更新诊断]` 的 `start` 到 `finish` 记录；同一个 `id` 表示同一次检查。最好同时保留最近一次成功的记录。

Windows 默认文件位于 `%LOCALAPPDATA%\HRToolkit\logs\HRToolkit_app.log`。自动检查、手动检查、复制下载地址分别有触发方式及操作类型，后台线程并发时不会共用检查编号。无需开启额外环境变量，也不会自动上传日志。

## 记录范围

- `start` / `finish`：操作、触发方式、检查编号、总耗时、完成或失败。
- `environment`：应用、系统、Python、SSL 版本、进程位数、是否安装包运行。
- `proxy_snapshot` / `opener_snapshot`：配置快照及已建立的 urllib opener 是否配置代理，不记录地址、密码；快照不能证明实际网络出口，也不能排除透明代理或按应用过滤。
- `configuration`：默认地址、安装目录配置或环境变量覆盖。自定义路径、URL 参数、凭据和本地路径不写入日志。
- `stage`：发行版查询、更新清单定位/读取、附件验证、版本比较等阶段。
- `request_start` / `response` / `request_end`：请求编号、脱敏接口、耗时、HTTP 状态、最终接口及是否发生重定向。不会输出完整重定向链或带签名的地址。
- 响应头只保留有限白名单，例如 Content-Type、Retry-After、服务端追踪编号、限流余量和 Server；未返回这些字段时不会编造。
- `error_sample`：错误响应最多读取一次、最多 4 KiB，沿用原请求的读取超时。只记录 HTML/JSON 特征、已知防护页标记和限流标记，不保存原文，不解压响应，不执行网页内容。读取失败不替换原来的错误。
- `fallback` / `retry`：记录现有备用查询、重试与恢复，不增加请求次数。
- `result`：没有新版本、发现新版、平台未发包、找到分享链接等结果。成功与失败都有记录。

## 如何判断

- HTTP 403 + `waf_marker=true`：响应中出现已知防护页标记，不代表已知具体拦截规则。
- `rate_limit_marker=true` 或限流响应头：可作为限流线索；应结合状态和重试提示，不把所有 403 都当作限流。
- `connection_error`：结合 `reason_type`、`errno`、`winerror` 或 `verify_code` 判断连接或证书问题，不输出可能携带凭据的原始异常正文。
- `json_invalid`：收到的数据不是有效更新 JSON；HTTP 200 不等于更新检查成功。
- 接口只给出空泛 403、没有标记/追踪编号：日志仍不能凭空确定是哪个防护规则或哪款本机软件拒绝，可能需要受控联网对照或联系服务方。

诊断写入使用现有日志大小限制（超过 1 MiB 后保留末尾约 256 KiB）。不采集 HR 表格、Cookie、授权令牌、完整错误正文，不常驻抓包，不增加后台探测。日志写入失败不影响更新结果。

## 验证边界

新增模拟响应回归用例覆盖成功、403 恢复/持续失败、读取失败、超时、证书错误、脱敏、并发编号隔离和日志写入失败；CI 已配置现代 Python 与 Win7 兼容栈的对应测试路由。

编写测试或配置 CI 路由不代表本地已经执行，也不代表已在出问题的 Windows 电脑确认根因。本次实际验证范围以交付说明为准。

2026-09-29 本地验证记录：

- 27 个定向用例通过：15 个诊断用例、8 个既有更新恢复/安全边界用例、1 个 CI 路由用例和 3 个 Qt 控制器触发/复制链接用例。
- 将修改前 HEAD 的更新模块与修改后模块分别注入相同模拟响应；8 个场景的成功返回值或错误类别、请求地址/方法/请求头/超时、请求次数、重试间隔一致。场景包括无新版、有新版、403 恢复/失败、超时恢复、无效 JSON、证书错误和清单重试。技术错误文本中的地址/异常正文做了脱敏，不要求这些文本逐字一致。
- 7 个修改/新增 Python 文件通过 Python 3.8 语法解析和当前解释器内存编译；`git diff --check` 通过。
- 未访问真实更新接口，未全量测试、构建、打包、提交或发布；本机 Qt 检查使用 macOS 的无界面运行环境，不代表 Win7/Win11 实机验收。真实 403 根因仍待安装新版后收集日志确认。

## v0.9.25 后的网络兼容修复

已提供日志显示：Gitee 最新发行版 API 和备用列表 API 均返回 HTML 403，包含 `baidu_waf_intercept_page`，服务器头为 `ADAS/1.0.214`。可确认收到防护页，但仍不能确定具体触发规则；没有限流标记也不等于排除了限流。

- 自定义 HTTPS 证书上下文补充 ALPN `http/1.1` 协商，证书、主机名验证保持开启。不支持 ALPN 的旧运行时保留原行为。
- Windows 下，只有固定公开 Gitee 最新发行版接口返回上述 HTML 403，且未出现限流标记或 `Retry-After` 时，才允许额外尝试一次 WinHTTP。浏览器/.NET 请求成功不证明 WinHTTP 必然成功，仍需实机确认。
- 有显式代理、PAC、自定义 urllib opener，或无法确认代理配置时跳过原生兼容请求，不绕过已知网络策略。无代理兼容请求使用 Windows 系统证书库和 TLS 1.2；不修改系统设置，不关闭证书验证，不使用浏览器身份、登录凭据或 PowerShell 子进程。
- 原生请求限定 HTTPS、固定接口，禁用自动重定向、Cookie 和自动身份认证；成功正文上限 2 MiB，失败正文采样上限 4 KiB。剩余时间预算传给每个阻塞阶段，系统 DNS/连接超时粒度可能超过预算。
- 正常连接不增加请求。兼容请求失败后仍走既有版本列表查询，不在列表、更新清单和安装包请求上反复尝试原生通道，也不把失败伪装为“没有新版本”。清单绑定、版本比较、平台选择和安装包 SHA256 校验不变。
- 日志增加 `transport_fallback` 和 `transport=winhttp` 的请求结束记录；`outcome=recovered` 只说明该次元数据请求恢复，最终成功以同一编号的 `finish` 为准。`transport_fallback_skipped` 表示网络策略不允许切换。
- Windows 构建号日志改用实际版本信息，避免兼容版本接口在 Windows 11 上报告 9200；此改动不影响安装包平台选择。

验收时在原先出错电脑点击一次检查更新，通过原有左下角日志入口查看本次 `start` 到 `finish`。若仍失败，提供完整这一段日志；不要反复卸载重装。真实服务持续拒绝时需要结合服务方防护记录排查，不能保证一次客户端兼容调整消除全部 403。
