# HR Toolkit 产品级 Review 与功能规划

> 2026-09 · 基于当前代码库（0.9.x，Qt 桌面端 + CLI）的产品视角完整评审。
> 本文不改代码，只做产品分析与规划。

---

## 一、产品现状理解

### 1.1 产品定位（实际状态，不是宣称状态）

**一句话定位**：面向甲方人事部门的、纯本地运行的**人事数据批处理工作台**——把每月重复的"收表 → 核对 → 拆合 → 汇总 → 提醒"链条自动化。

三个决定产品边界的硬约束（所有规划都必须服从）：

1. **数据不出本机**：身份证、工资、保单全程本地处理，日志脱敏。这是产品核心信任卖点。（已确认的例外：AI 对话助手经甲方明确同意使用云端大模型，见第五部分。）
2. **Win7 SP1 兼容**：甲方现场存在老电脑（Python 3.8 + 旧 Qt 栈），任何新依赖都要过这道门。
3. **单人单机使用**：无账号体系、无协作、无云端。用户是"一个人对着一堆 Excel"。

### 1.2 目标用户与场景画像

- **执行层（人事专员）**：每月固定时间跑批——收各项目部异动表、收 HR 系统考勤导出、收社保缴费清单、合并工资表。痛点是格式乱、人员对不上、漏交错交查不出来。
- **审核层（人事主管）**：看汇总结果和异常，向领导汇报。痛点是每次都要打开多个 Excel 自己找数。
- **业务特征**（从需求命名可推断）：项目型/工程型企业——"项目部""入职公司""参保地""缴纳单位"高频出现，人员分散、异动频繁、社保跨公司缴纳。这解释了为什么"按身份证关联"是全产品的主键逻辑。

### 1.3 核心功能盘点

**业务工具（4 组 11 个入口）**：

| 分组 | 工具 | 处理对象 | 估计频次 |
| --- | --- | --- | --- |
| 社保与保险 | 社保明细与汇总 | 社保清单 + 花名册 | 月度·高频刚需 |
| 社保与保险 | 保险台账与增减预警 | 保单清单 + 人力资源分析表 | 按保单周期·中频 |
| 考勤与统计 | 考勤与周月报统计 | HR 系统导出 | 周/月·高频刚需 |
| 薪酬管理 | 工资表按公司拆分 | 月度工资表 | 月度·高频刚需 |
| 薪酬管理 | 多月工资合并 | 多月工资表 | 月度·高频刚需 |
| 人员与档案 | 异动表汇总 | 各项目异动表 | 月度·高频刚需 |
| 人员与档案 | 花名册更新（独立入口） | 异动汇总表 + 花名册 | 月度·高频 |
| 人员与档案 | 档案入库 | 档案移交表 | 按移交节点·中低频 |
| 人员与档案 | 档案表生成 | 档案汇总表 | 低频 |
| 人员与档案 | 员工资料 OCR 打包 | 混乱资料库 | 入职季集中·低频重活 |
| 人员与档案 | 资料文件夹改名 | 人员资料目录 | 整理期·低频 |

**工作台底座能力（容易被低估的部分）**：项目工作区（批次/上传资料/处理结果/补充资料/回收站）、SHA-256 校验与原子提交、历史索引与一键复用、运行日志（脱敏、可复制）、单次运行异常提醒、工资列头映射学习、OCR 缓存与"资料待确认"闭环、双语界面、自动更新（Gitee/GitHub 双源）、内置教程。

**结论**：这已经不是"九个小工具"，底座已经具备工作台雏形。短板不在单个工具的能力，而在**跨工具的连续性**（见下节）。

## 二、功能关系问题诊断

### 2.1 人员主数据是隐性枢纽，但没有统一入口

花名册/人力资源分析表被至少 5 个工具（社保、保险、异动、花名册更新、资料打包）分别要求单独选择。同一个"人员真相源"每月被用户搬运 5 次。这是当前链路最长的根源——**工具间传递靠人肉，人员数据是暗线**。

### 2.2 导航条目复用同一标题

"异动表汇总与花名册"和"档案入库与档案表"在左侧导航各出现两次（同一工具的两个 variant）。老用户没问题，新用户第一次点开会困惑"为什么有两个一样的"。低成本可修，收益是降低培训成本。

### 2.3 跨工具链路长且断点在"中间结果搬运"

典型月度全流程：异动汇总 → 花名册更新 → 社保汇总 / 保险台账 / 工资合并。中间结果必须人工重新作为输入选择（"从历史复用"部分缓解，但用户得记得哪一步产出什么）。月度例行动线没有整体视图，工具是好的，**动线是散的**。

### 2.4 OCR 打包与其他工具零联动

新员工链路天然是：入职（异动增员）→ 资料收集（OCR 打包）→ 档案入库 → 花名册。目前四步各自独立，OCR 识别出的"身份证号 + 姓名 + 材料类型"其实是最干净的结构化数据，却只用于打包。

### 2.5 异常提醒是"一次性"的

result notices 只存在于单次运行结果里，用户看完即走。人事实际需要一个**项目级的"待处理异常清单"**：本月社保 3 人未匹配、2 人姓名不一致、保险 1 人需加保——这些是真正要打电话、找项目部核实的活，现在散在各个批次的 Excel 和日志里，没有闭环（谁处理了？处理完了吗？）。

## 三、现有功能的体验优化空间

按投入产出排序：

1. **结果摘要卡**：处理完成只在结果区给文件，用户仍要打开 Excel 才知道"多少人、几条异常"。在完成通知里直接给关键数字（人数/未匹配/异常计数），审核层价值极大。实现成本低（数据都在 result 结构里）。
2. **导航命名与排序**：去重同标题条目；组内按"月度高频在前"排序。
3. **搜索升级**：项目文件区搜索目前只覆盖文件名。异常文本、OCR 索引内容、Excel 关键列值搜不到（"张三的资料在哪个批次"目前无解）。
4. **首次使用引导**：教程有，但"第一次跑社保"要理解花名册、账单期、参保地三个概念，可以做一次性分步引导。
5. **信息架构深度**：回收站/历史/批次层级较深，高频操作（找上个月的结果）与低频操作（恢复回收站）平铺在一起。

## 四、功能规划（P0 / P1 / P2）

> 原则：每个功能必须回答"每月被用几次、省多少人工、出错率降多少"。明确**不建议做**的：云同步/多人协作（违背离线定位）、移动端、自由报表设计器、通用数据查询语言。这些是另一个产品。

### P0 —— 非常实用，建议近期做

#### P0-1 项目级异常中心（待办清单）

- **解决什么问题**：异常散在各批次结果里，无追踪、无闭环。
- **典型场景**：月初处理完社保+保险+考勤，把所有"未匹配/姓名不一致/需加保/漏打卡"汇总成一张项目级清单，逐项核实、标记"已处理"，月底清零。
- **用户价值**：把"查错"从翻 Excel 变成清待办；这是人事每月真正的隐形工作量。
- **现有基础**：result notices、历史索引（SQLite）、批次清单都已存在，只差聚合视图与状态字段。
- **实现复杂度**：中（聚合已有数据 + 简单状态持久化）。
- **影响**：纯新增 UI/存储，不影响业务处理路径。
- **建议**：现在做，是底座数据红利的直接兑现。

#### P0-2 结果摘要卡

- **解决什么问题**：处理完必须打开 Excel 才知道结果好坏。
- **典型场景**：工资合并完成，直接显示"覆盖 312 人 / 12 个月 / 新增 8 人 / 0 条异常"。
- **用户价值**：审核层 30 秒判断"这次跑得干不干净"。
- **现有基础**：各工具 Result 对象已有结构化指标（人数、公司数、warnings）。
- **实现复杂度**：低。
- **影响**：无。
- **建议**：现在做，几乎是免费的价值。

#### P0-3 模板漂移自检（输入体检）

- **解决什么问题**：项目部交上来的表头悄悄变了，跑完才发现大面积未匹配。
- **典型场景**：上传时即提示"此文件与上月模板相比多了 2 列 / 应发列名变化"，与已学习的列头规则联动。
- **用户价值**：把"跑完失败再排查"变成"上传时拦截"，这是出错率降低最大的一项。
- **现有基础**：工资合并的列头映射学习 + 记忆机制已经成熟，推广到社保/考勤/异动。
- **实现复杂度**：中。
- **影响**：只做预警不阻断，不影响现有处理。
- **建议**：现在做（可先覆盖社保和考勤两个高频工具）。

#### P0-4 AI 对话助手 v1（详见第五部分）

- **定位**（甲方已确认需求）：自然聊天 + 多表对比分析（"这两张表有什么区别、谁的增长值更好"）+ 工具使用指导（"这个功能怎么用/我该用哪个工具"）。
- **实现复杂度**：中（云端 LLM 客户端 + 本地 Excel 解析管道，均为成熟技术）。
- **建议**：现在做，直接以云端 LLM 为核心，不做本地检索式过渡形态。

### P1 —— 有明显价值，适合下一阶段

#### P1-1 人员主数据中心（统一花名册挂载）

- **解决什么问题**：花名册被 5 个工具重复选择、重复搬运。
- **典型场景**：项目设置一次"主花名册"，社保/保险/异动/资料打包自动引用；花名册更新后全工具同步用新版。
- **用户价值**：月度动线省一半操作步骤；数据一致性有唯一真相源。
- **现有基础**：项目工作区 + 批次引用机制（"从历史复用"已是文件引用）。
- **实现复杂度**：高（涉及各工具输入约定、版本快照策略）。
- **影响**：要动各工具的输入逻辑，需谨慎设计向后兼容；处理性能不受影响。
- **建议**：下一阶段做，是"工具箱→工作台"的关键一步，但要在异常中心等先行验证后。

#### P1-2 月度流程向导（月结助手）

- **解决什么问题**：月度例行动线长、顺序靠人记。
- **典型场景**："开始本月月结"→ 按异动→花名册→社保→考勤→工资的顺序，逐步引导选文件、跑批、看异常，每步可跳过。
- **用户价值**：新员工零培训上手；老人不漏步骤。
- **现有基础**：工具注册表 + 批次历史完整。
- **实现复杂度**：中高（编排 UI，不改业务逻辑）。
- **影响**：纯编排层，风险可控。
- **建议**：与 P1-1 配套设计。

#### P1-3 证件/合同到期提醒

- **解决什么问题**：身份证过期导致社保缴纳失败、合同到期漏续签。
- **典型场景**：从花名册扫描身份证有效期/合同到期日/试用期，启动时或手动触发给出 30/60/90 天预警清单。
- **用户价值**：高频刚需——这是每月真实会出事故的点，且纯读取计算。
- **现有基础**：花名册读取、身份证解析（OCR 工具已有 18 位身份证处理逻辑）。
- **实现复杂度**：低中。
- **影响**：无。
- **建议**：作为 P1 里性价比最高的一项，甚至可提前进 P0。

#### P1-4 全项目内容搜索

- **解决什么问题**："张三的劳动合同在哪个批次？"现在无解。
- **典型场景**：搜人名/身份证后四位，跨批次、跨结果、含 OCR 缓存索引。
- **现有基础**：OCR 内容索引、SQLite 历史库。
- **实现复杂度**：中。
- **建议**：真实需求出现时排期。

#### P1-5 月度汇报导出

- **解决什么问题**：向领导汇报要手工摘数。
- **典型场景**：一键生成本月人事处理简报（异动人数、社保异常处理情况、考勤统计摘要），Word/Excel 格式。
- **实现复杂度**：低中。
- **建议**：异常中心落地后顺理成章，因为素材都在。

### P2 —— 可选增强，有明确需求时再做

| 功能 | 说明 | 复杂度 | 触发条件 |
| --- | --- | --- | --- |
| 花名册月度 diff | 本月 vs 上月人员增减对比视图 | 低中 | 异动汇总已覆盖大半，用户明确提出对比需求时 |
| 结果内嵌只读预览 | 不开 Excel 直接看结果网格 | 高 | 用户反复抱怨打开外部 Excel 慢时 |
| 项目模板 | 新建项目时复制标准目录结构 | 低 | 多项目/多年份使用成为常态时 |
| 批量打印/水印 | 合同或通知单批量处理 | 高 | 与人事场景关联弱，除非甲方点名 |

**明确不建议做**：云同步、多人协作、账号体系、自由报表设计器、通用自然语言查询全部本地数据（隐私与技术双重风险，收益不明确）。

### 高频刚需 vs 锦上添花（汇总）

- **高频刚需**：社保、考勤周月报、工资拆分/合并、异动汇总、花名册、（应补：到期提醒、异常闭环）
- **中频实用**：保险台账、档案入库、历史/批次复用
- **锦上添花**：OCR 打包（入职季刚需但低频）、改名、双语、回收站、外观设置

### 减人工 / 降错误 / 提批量效率的贡献排序

1. 模板漂移自检（降错误，前置拦截）
2. 异常中心（减人工，闭环核销）
3. 人员主数据中心 + 月结向导（减人工，缩短链路）
4. 结果摘要卡（提审核效率）
5. 到期提醒（防事故）

### 工具箱 → 一体化工作台的升级路径

四步走，每步独立可用、逐步加深集成：
**异常中心（聚合层）→ 人员主数据（数据层）→ 月结向导（流程层）→ 汇报导出（输出层）**。AI 助手横向贯穿，作为交互层。

## 五、AI 对话助手专项分析

### 5.1 前置判断：AI 在这个产品里的真实定位（按甲方最新需求修订）

甲方对 AI 的需求是三件具体的事：

1. **多表对比分析**：上传两张或多张表格 + 一句自然语言描述（"这两张表有什么区别？""谁的增长值更好？"），AI 直接给出分析结论。
2. **工具使用指导**：某些工具甲方不会用，直接问 AI，要说人话讲明白——包括"我想干 XX 该用哪个功能"。
3. **自然聊天**：通用对话能力。

这彻底改变了 AI 助手的产品定位：它不是附属帮助系统，而是**继 11 个工具之后的第 12 个、也是唯一不需要学习成本的工具**。它绑定四类真实时刻：

1. **数据时刻（核心）**：手里有 2+ 张表，想直接问差异和增长对比——这类需求很多是临时性、一次性的问数，根本不值得做成固定工具，对话式分析恰好是正确形态。
2. **困惑时刻**：第一次用、忘了规则（"周报到底几点算超时？""这个功能是干嘛的？"）。
3. **出错时刻**：跑完有异常/失败，需要"为什么"和"怎么办"。
4. **汇报时刻**：需要把处理结果组织成语言（给领导的说明、给项目部的催收话术）。

### 5.2 UI 位置分析（结合当前布局实测）

当前主窗口结构：左侧悬停侧栏 248px（≤1224px 自动收起）· 中间表单区（最大阅读宽 820px，右栏展开时预留 640px）· 右侧项目文件栏 320–360px（窄窗自动收起）· 窗口最小 760×600 · 首选 1600×900。

各方案对比：

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| 右侧第三栏（并列） | 与项目栏同层级 | 中间表单被挤到 <640px，与现有响应式阈值（1224/976px）正面冲突，窄窗必然崩 | ❌ 不可行 |
| 底部面板 | 常见于 IDE | 对话阅读需要高度而非宽度；与进度条/结果卡抢纵向空间；宽幅气泡排版差 | ❌ 不推荐 |
| 独立页面（导航新条目） | 隔离干净 | 违背"随时可问"的定位，切换成本高 | ❌ 不推荐 |
| **右侧覆盖式抽屉（overlay，不挤布局）+ 可弹出独立窗口** | 不改变任何现有布局计算；窄窗下纯覆盖不挤压；需要对照项目文件时可弹出为独立窗口（双屏/大屏友好） | 需要处理好与项目栏的同时展开（互斥或共用右侧） | ✅ **推荐** |

**推荐方案细节**：

- **默认形态**：右侧滑入抽屉，宽 340–380px，**overlay 悬浮于内容之上**，绝不参与主 RowLayout 的宽度分配——这直接规避了项目里反复出现的 QML 布局循环告警问题（宽度互相依赖是历史红灯来源）。
- **与项目栏互斥**：AI 抽屉打开时项目栏自动收起（同一右侧区域，一物一用）；AI 抽屉关闭后项目栏按原状态恢复。
- **弹出独立窗口**：抽屉右上角"弹出"按钮，转为独立 Qt 窗口，可拖到副屏、贴边。老电脑单屏用户不用此功能也不受影响。
- **入口三处**：① 侧栏底部按钮（更新卡片上方）；② 运行结果卡/异常提醒旁的"问助手"快捷按钮（场景化入口，最重要）；③ 全局快捷键（如 Ctrl+K / F1）。
- **窄窗与低分辨率**：760×600 最小窗口下抽屉以覆盖形式打开，主界面不动；用户觉得碍事可直接关。窗口 <980px 侧栏已收起，AI 按钮仍在侧栏触发区可见。不做悬浮球（增加常驻渲染负担，Win7 老机器不友好）。

### 5.3 能力分层：v1 该做什么、不该做什么

**v1 必做（按甲方需求直取核心）**：

| 能力 | 说明 | 实现要点 |
| --- | --- | --- |
| 自然聊天 | 通用 LLM 对话，带人事业务背景的 system prompt，不装傻不越界 | 云端 LLM，无额外管道 |
| **多表对比分析（核心）** | 对话框直接附加 2+ 张 Excel + 一句描述，AI 回答差异、增长对比、异常点 | 本地 openpyxl 解析 → 结构化（markdown/CSV）→ 发送 LLM，详见 5.4 |
| 工具使用指导 | "工资怎么按公司拆？" → 结合内置教程 RAG，说人话解释 + 附"去处理"跳转 | 已有教程/规则文档做检索素材 |
| 运行结果/异常解读 | "本次 3 条未匹配的原因是…建议检查花名册身份证列" | result notices + warnings 结构化注入 |
| 处理总结生成 | 把批次摘要组织成可复制文字（汇报话术） | Result 结构化指标 |
| 推荐并跳转工具 | "我想把工资按公司拆开" → 跳到对应工具；**只跳转填参，不代执行** | 工具注册表 + 表单规格 |

**v1 明确不做（并说明理由）**：

1. **自然语言直接执行工具**——批处理会写文件，误触发代价高；即使后续版本也应保持"AI 预填参数 + 用户确认执行"。
2. **OCR 内容问答**——缓存索引面向匹配不面向语义，且让 AI 理解扫描件属于第二个产品的工作量。
3. **多轮 agent 任务编排**——月结向导（P1-2）用确定性流程做更可靠。
4. **本地大模型**——Win7/4GB 内存环境不可行，安装包从 <100MB 涨到 GB 级，直接否掉。
5. **报表设计器化**——对话分析保持"用户提问驱动"的轻形态，不要演变成自由报表/BI 平台，那是维护无底洞。

### 5.4 架构设计：云端 LLM 为核心（甲方已确认数据可上云）

隐私不再作为架构约束（甲方已明确接受），设计目标变为：**接哪家都能用、大表发得动、结果答得准、成本可控**。

**① 云端 LLM 接入：四家预置（甲方已采购余额，直接接入）**

- 四家均提供 **OpenAI 兼容 Chat Completions 接口**，实现一个标准客户端即可同时接入，且均为国内服务，无代理/网络合规问题。接口地址与模型清单**全部内置**，用户只需填 API Key。
  - **DeepSeek**：`https://api.deepseek.com/chat/completions`，默认 `deepseek-chat`（另有 `deepseek-reasoner`）；中文表格理解好、价格低。
  - **MiniMax**：`https://api.minimax.cn/v1/chat/completions`，默认 `MiniMax-M3`；M3 支持图片，M2.x 系列纯文本。
  - **智谱 GLM**：`https://open.bigmodel.cn/api/paas/v4/chat/completions`，默认 `glm-4.6`；视觉模型 `glm-4.6v` / `glm-5.3-flash` / `glm-4v-flash`。
  - **通义千问（阿里云百炼）**：`https://dashscope.aliyuncs.com/compatible-mode/v1/chat/completions`，默认 `qwen-plus`；视觉模型 `qwen3-vl-plus` / `qwen-vl-max` / `qwen-vl-ocr`。
  - 注意各家版本段不同（GLM 是 `/api/paas/v4`、百炼是 `/compatible-mode/v1`），所以「只填域名」时的补全按服务商预设走，不能一律拼 `/v1`。
- 架构上仍只实现一套 OpenAI 兼容协议（Base URL + API Key + 模型名），加服务商只是增加一个预置项，代码零改动。
- API Key 由甲方配置，只存本机设置文件，不进日志、不进崩溃上报；设置页提供服务商切换与连通性测试，模型菜单里也能直接切服务商与模型（每家各有自己的一份 Key 与模型列表，互不覆盖）。
- 预置清单以外的模型（自建网关、自定义端点）仍可手工添加，上限 40 个/服务商。

**② Excel 解析管道（这是产品差异化的关键，不是简单"传文件"）**

```text
用户附加文件（.xlsx / .xls，复用现有 excel_compat 三级转换）
  → 本地 openpyxl 解析：识别表头行位置（复用工资合并已有的表头探测经验）
  → 转成 LLM 友好的结构：markdown 表格 / CSV + 每列类型摘要（数值/日期/文本）
  → 体积控制：按行数分片；超大表先按用户问题做本地聚合再发送
  → 携带问题发送 → AI 返回对比结论 + 差异明细表
```

- **大表策略（决定成败）**：不设好这个，甲方第一张 5000 行的工资表就会把对话打爆。规则建议：≤500 行整表直发；500–5000 行自动分片多轮或按关键字段（如部门/月份）本地预聚合后发送摘要；>5000 行提示用户缩小范围或改用内置工具跑批。
- **分析结果的可靠性**：数值对比类问题（增长值、差值、合计）先在本地用 Python 算出确定性结果，再让 LLM 做**解读**而非**计算**——LLM 算数不可信，本地算+AI 解释才是正确分工。这是"答得准"的核心设计。
- 同一附件在会话内缓存解析结果，多轮追问不重复解析、不重复计费 token。

**③ 工具指导的知识注入**

内置教程 + README 规则 + 工具表单规格本身就是高质量 RAG 素材（而且量小，可直接全量注入 system prompt，不需要向量库）。AI 回答"这个功能怎么用"时永远基于真实文档，不靠模型幻觉。

**④ 合规备注（一句话，不作为阻断）**

数据上云已获甲方确认；建议设置页保留一个可选的"发送前自动打码"开关（身份证/手机号/银行卡正则替换）作为后续增强，供甲方按自身合规要求决定是否开启。

### 5.5 性能、体积与成本约束下的设计

- **启动速度**：AI 面板 QML 用 Loader 按需实例化（首次打开才创建），LLM 客户端代码首次使用时才 import，不进主启动路径。启动耗时零增加。
- **内存**：对话记录设上限（如 200 条，超限淘汰最旧）；消息列表用现有虚拟化列表模式（项目已有 3 万行虚拟滚动经验）；附件只保留解析后的精简结构（非原始单元格对象），关闭抽屉释放。
- **安装包**：仅 HTTPS 调用代码（stdlib urllib 即可，certifi 已随更新器内置），<100KB，无任何本地模型。
- **成本控制**（按 token 计费后的新课题）：附件解析结果设 token 上限；会话历史超过 N 轮自动裁剪早期上下文；本地算、AI 解释的分工本身就把最贵的"整表重读"压缩掉了；对话界面显示本次消耗 token 量级，让甲方对账单有预期。
- **网络**：离线时 AI 入口明确提示"需要联网"，主工具不受任何影响。

### 5.6 Win7 / Win11 兼容性

- QML 仅用 2.15 特性集（与现有 Main.qml 一致），不用高版本控件。
- 视觉保持平面简单样式（现有 AppButton/AppTextField 体系），不用模糊/亚克力特效——Win7 下既不兼容也耗性能。
- HTTPS 依赖 certifi（已内置），Python 3.8 语法完全覆盖。
- 中文输入法复用现有 AppTextField（已在产线验证）。
- 独立弹出窗口是基础 Qt Window 能力，Win7 原生支持。
- 发布前按既有流程跑 Win7 SP1 干净虚拟机冒烟（`smoke_win7_installer.ps1`）。

### 5.7 交互方案要点

- **输入区带附件能力**："+"按钮选择 Excel（支持 .xlsx/.xls），也支持直接把文件拖进对话框；附件以 chips 展示文件名 / sheet 名 / 行数，可单独移除；多附件即"多表对比"模式。
- **建议问题随场景更新**：首次打开展示 chips——"对比这两张表的差异""谁的增长值更好？""周报几点算超时？""我想按公司拆工资表该用哪个功能？"
- **分析结果可回显、可导出**：AI 回答中的差异明细以小表格渲染（虚拟化列表），提供"导出为 Excel"落盘到当前项目批次——分析结论从"聊完就丢"变成可留存的工作成果。这一步让 AI 和项目工作区真正打通。
- **工具指导带动作卡**：解释 + "去处理"按钮（跳转工具并预选文件），执行权永远在用户手里。
- **出错场景零输入**：异常提醒旁的"问助手"按钮自动携带该批次上下文。
- **流式输出**：回答逐字渲染（SSE 流式），大表分析等待期间显示"已解析 2 个文件、共 3,412 行"的进度状态。
- 对话内容可一键复制（与运行日志的复制交互保持一致）。

### 6.1 AI 助手 v1 实施拆解（技术路线）

按"后端核心 → 前端集成 → 增强"三个里程碑推进，每个里程碑独立可用、可验收；全程遵守项目验证边界（仅最小语法/编译检查，CI scope 映射同步登记新模块）。

**M1 后端核心（纯新增 Python，零 UI 风险）**

- `hr_toolkit/ai/config.py`：服务商预置（DeepSeek/MiniMax/智谱 GLM/通义千问）、地址补全与校验、Key 存取（本机设置文件）、连通性测试。
- `hr_toolkit/ai/client.py`：OpenAI 兼容流式客户端（stdlib urllib + certifi，SSE 流式渲染；Python 3.8 语法）。
- `hr_toolkit/ai/excel_context.py`：Excel → LLM 上下文管道——复用 `excel_compat` 处理 .xls，复用表头探测经验，输出 markdown 表格 + 列类型摘要；行数分级（直发/分片/预聚合）。

**M2 前端集成**

- `controller.py` 增加会话管理桥接（发送/流式回传/附件管理），QML 用 Loader 按需实例化 AI 抽屉。
- 抽屉 UI：右侧覆盖式 340–380px、与项目栏互斥、可弹出独立窗口（5.2 方案不变）。
- 输入区"+"附件按钮 + 拖拽、附件 chips（文件名/sheet/行数）、建议问题 chips、流式气泡。

**M3 增强（可拆到后续版本）**

- 分析结果导出 Excel 落当前批次；异常提醒旁"问助手"入口带批次上下文；本地数值计算 + AI 解读分工；token 消耗显示。

**验收口径**：M1 完成即可演示"命令行里两张表对比分析"；M2 完成即甲方可见的成品；M3 按反馈迭代。

**总判断**：这个产品的工具层已经做得又深又扎实（列头学习、OCR 缓存、批次原子性都是同类工具里少见的工程完成度）。接下来的价值不在加第九、第十个工具，而在**把已有数据和批次串成动线、把异常变成闭环、把规则变成随问随答**——从"人事的 Excel 处理器"升级为"人事的月度工作台"。而 AI 对话助手按甲方最新需求（多表对比分析 + 工具指导 + 自然聊天）落地后，是第 12 个工具，也是唯一零学习成本的入口：**固定的、规则明确的活交给 11 个工具，临时的、一句话的问数交给 AI**——这两层合起来，才是对"一体化工作台"的完整回答。
